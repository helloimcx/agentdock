# 多种 Agent 运行时下的 Mesh 工作区与执行边界

## 目标

让配对 Mesh 节点的批准根目录成为所有 Mesh 文件操作的唯一访问范围，同时如实告诉 Agent：运行时本身在哪里运行，每类操作会在哪里执行。成功的文件操作必须作用于设备；失败或不受支持的操作不能悄悄改为读写 Local AI Core 宿主机上的影子工作区。Shell 是单独授权的能力：它从批准根目录启动，但设备不会通过操作系统权限把它限制在该目录内。

## 范围

- 覆盖仓库当前注册的所有 Agent 类型，包括动态注册和静态支持的运行时：Claude Code、Codex、Pi、OpenCode、Hermes、LocalCore ACP、Cursor、Gemini、Qoder 和 iFlow。运行时清单必须从当前注册表生成，不能把这里的列表当作永久完整的清单。
- 在已认证的 Mesh 能力之上提供一套与运行时无关的 Mesh 工作区文件代理。ACP 标准文件请求和各运行时自己的文件工具适配器共用这套代理。
- 使用每个运行时实际支持的系统指令机制，向 Agent 说明真实的 Mesh 执行边界，包括宿主机控制面、远程执行目标、已路由的工具、路径规则、记忆归属和失败行为。不能声称 Agent 进程本身运行在 Mesh 节点上。
- 从同一份运行时 Mesh 策略生成 Agent 看到的工具和能力清单，并据此配置适配器；提示词不能宣称某项操作会在设备上执行，除非执行层确实保证这一点。
- 为每种运行时明确文件操作如何接管或替换。必须把工作区文件工具路由到代理，或可靠地禁用/替换宿主机本地工具并提供代理适配器。不能把提示词、MCP 是否可用、显示名称或某个 provider 配置项单独当作可靠的执行保证。
- 如果某运行时没有经过验证的接管或禁用/替换机制，就拒绝启动它的 Mesh 会话，并说明缺少什么能力。绝不悄悄回退到服务器上的影子工作区。
- Agent 运行时目录、配置和私有/持久记忆仍由宿主机管理，与 Mesh 工作区文件访问分开。AgentDock 工作区记忆服务也必须放在明确归 Core 所有的记忆目录中，不能放进 Mesh 影子目录，也不能把它当普通工作区文件路由到设备。
- 保留现有 Shell 代理作为一项单独授权的设备能力；文档要说明批准根目录只是 Shell 的起始目录，并非沙箱边界。
- 更新 Mesh 和架构文档，说明运行时如何执行路由，以及记忆由谁保存。

## 不在本次范围内

- 不改变普通本地运行或 OpenSandbox 中的文件操作方式。
- 不扩大 Mesh 文件能力的访问范围，不增加任意绝对路径访问。Shell 仍是独立能力，使用配对设备用户本身的操作系统权限。
- 不把易变的设备状态（PID、守护进程是否运行、当前步数）当作持久记忆。这类信息必须带观测时间，并在使用前重新查询确认。
- 不恢复已经移除的通用 Mesh Shell MCP 工具。

## 行为与接口

- 向 Agent 明确说明两个角色：
  - **宿主机控制面**：ACP Agent 进程、运行时安装目录、凭证/配置和 Agent 私有持久记忆都运行或保存在 Local AI Core 宿主机上。
  - **远程执行目标**：选定的 Mesh 节点拥有项目工作区文件。Mesh 文件能力只能访问该节点批准的根目录。如果 Core 和节点分别授权了 Shell，Shell 会从该目录启动，但仍使用配对设备用户本身的操作系统权限；该用户能访问的其他路径或网络资源也可能可用。Agent 是通过 Mesh 控制目标设备的，Agent 进程本身并没有运行在设备上。
- 运行时上下文根据节点信息和生效的能力/路由策略生成，说明设备名称、平台、哪些操作会路由到设备、哪些记忆仍保存在宿主机，以及设备离线或操作不受支持时会返回错误而不是切回宿主机。不能仅凭平台名称暴露凭证，或声称 Agent 能访问 Android 特有功能或整个系统。
- 兼容表要列出各运行时具体如何收到指令。不能假设每个运行时都会遵循通用 ACP 元数据字段；必须使用运行时实际支持的系统提示或配置方式。如果无法送达最低限度的边界说明，就拒绝启动。
- `MeshWorkspaceFilesystem` 是工作区 `read`、`write`、`edit`、`list` 和有界 `glob` 操作的分发边界。这些操作通过认证后的 Mesh 文件能力执行，并受节点批准根目录限制；不能回退到服务器影子目录读取或写入。Shell 是独立能力，不能描述成受批准根目录限制。
- 如果 ACP 宣告了 `fs/read_text_file` 和 `fs/write_text_file`，这两类请求也调用上述文件代理。
- 每个 `AgentRuntimeDefinition`（或其引用的适配器注册表）都要声明明确的 Mesh 文件策略和能力要求。运行时适配器要么把原生文件操作转换成代理调用，要么禁用/替换宿主机本地文件工具。实现必须依据运行时实际的工具注册和权限生命周期，而不是猜测工具名称。
- 如果无法安全接管或禁用某个运行时的文件工具，Mesh 启动必须失败，并说明运行时名称和缺失的约束能力。兼容矩阵要与当前运行时注册表保持一致。
- 路径相对于节点批准根目录。绝对路径、目录穿越、符号链接逃逸、不支持的操作、节点断连和超出限制都要返回明确错误。
- Agent 私有记忆和运行时状态使用各自独立的宿主机路径或 API；它们不属于工作区文件操作，也不会通过文件代理暴露给 Mesh 节点。在移除或重新定义影子目录之前，Core 工作区记忆必须迁移或绑定到明确归 Core 所有的目录。
- 给 Agent 的说明只是操作指引，不是安全边界。真正的路由、工具禁用、权限检查、路径限制和失败关闭都由提示词以下的运行时适配器与 Mesh 文件代理执行。

## 约束与兼容性

- 保留现有 Mesh 协议和节点能力白名单；只有当实现清单证明必须增加能力时才扩展协议，并明确版本化和记录。
- 只有当文件路径已证明会被正确路由或明确失败时，才能将某运行时称为 Mesh 兼容。
- 保留每种运行时自己的目录和配置语义，同时避免它们与远程工作区根路径指向同一位置。
- 文件能力请求受节点批准根目录限制。Shell 从该目录启动，但使用设备用户本身的操作系统权限；Agent 上下文和运行时适配器都要如实说明这一点。
- 普通本地运行和 sandbox 会话保留当前文件访问行为，不附加 Mesh 专属限制。

## 验收标准

1. 根据所有已注册运行时生成兼容矩阵，并说明执行约束机制和验证范围。Claude Code、OpenCode 和 Pi 已配置适配器，并有仓库级测试覆盖；这不代表已对 provider 二进制完成端到端验证。Codex、Hermes、LocalCore ACP、Cursor、Gemini、Qoder 和 iFlow 在文件操作约束通过验证前明确禁止用于 Mesh。参见[运行时兼容矩阵](../architecture/mesh-runtime-compatibility.md)。
2. 每种可用运行时都通过该运行时已验证的机制收到边界说明。说明 Agent 进程和记忆仍在宿主机、选定的设备目标、设备上可用的操作、文件工具的相对路径规则，并指出可选 Shell 不受 OS 沙箱约束。不能有运行时提示词声称 Agent 进程在 Mesh 节点上。
3. 对每种已标记为 Mesh 可用的运行时，create/write/read/edit/list/glob 只影响配对节点批准根目录中的内容，宿主机影子目录中的哨兵文件保持不变。
4. 对无法约束文件操作或无法收到最低限度真实上下文的运行时，Mesh 会话创建必须给出可执行的错误说明并失败，不能让工作区操作落到宿主机影子目录。
5. 绝对路径、目录穿越、符号链接逃逸、节点离线、不支持的操作以及大小/遍历限制都要明确失败，不能回退。
6. Agent 私有记忆与 Core 记忆跨会话保留在宿主机上，与 Mesh 工作区路由隔离，且不会创建或修改设备工作区文件。Mesh Core 工作区记忆放在独立于影子目录的 Core 用户数据目录；首次访问时复制旧 Markdown 文件并保留原件以便恢复。设备产生的易变状态要标明观测时间，在作为当前信息展示前重新检查。
7. 普通本地和 sandbox 会话保持现有行为。
8. 当前架构事实、Mesh 架构文档、唯一的语义变更记录、架构图源文件和导出物、总览、README 图示及 README 的 New 说明都与实际实现一致。
